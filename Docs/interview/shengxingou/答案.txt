第5题：Agent 与后端数据的一致性设计

【题目】

第5题：Agent 与后端数据的一致性设计

传统后端的数据存储都是放在后端。但 Agent 时代，大部分业务逻辑放到 Agent，后端的角色发生了变化，数据很容易变成 Agent 存一份，后端存一份。要如何设计？

【摘要】

在 Agent 架构中，业务逻辑由 Agent 承担，传统后端仅负责持久化与事务处理。若 Agent 同时维护业务数据副本，将形成双数据源，导致数据不一致。该问题的本质是数据归属划分，而非数据同步。本方案的核心设计如下：后端作为业务数据的唯一权威源（System of Record），Agent 仅持有执行状态（对话上下文、任务计划、checkpoint）与可失效的数据缓存；所有业务写操作统一收敛至后端 API，配合幂等键与乐观锁保证操作安全；后端数据变更通过事件机制推送至 Agent 刷新上下文；崩溃恢复采用 checkpoint 恢复与业务状态重读相结合的机制，并以定期对账作为最终一致性兜底。后端的角色由业务逻辑执行者转变为事实源、能力网关与安全边界。

【全文】

一、问题解析

1. 问题定位：数据归属问题，而非同步问题

传统架构中，数据同步问题以双数据源均合法为前提，目标是保持两份数据一致。而本问题的核心风险在于同一事实出现两个不同表述：Agent 认为订单已创建，后端数据库中并无该记录。此类矛盾无法通过同步解决，必须通过消除多余数据源解决。

因此，问题的准确表述为：当 Agent 承担业务决策与编排职责，传统后端承担持久化与事务处理职责时，如何划分数据归属，避免多数据源冲突。

从架构视角看，Agent 可抽象为一个具有记忆能力、执行多步任务、存在重试行为且可能中途失效的客户端。不可信客户端、超时重试、并发冲突与状态恢复均为分布式系统中的经典问题，Agent 架构将其重新引入核心位置。

2. 不一致的成因

Agent 的四个特性导致数据不一致风险：

- 记忆机制：Agent 将业务数据复制至上下文，副本随业务变化而失效；
- 多步执行：任务分多步完成，中间状态分散于 Agent 内部，缺乏统一管理；
- 重试行为：请求超时后自动重试，后端可能已成功处理首次请求；
- 进程失效：崩溃后状态丢失，任务进度与已执行操作均不可追溯。

3. 数据盘点

Agent 侧状态数据：对话上下文、长期记忆、任务进度、推理结果、执行计划、中间产物。
后端侧业务数据：用户、订单、库存、账户余额、任务状态等业务事实。

判定标准：业务数据为多用户、多系统共享的事实；Agent 状态数据仅服务于 Agent 自身的推理过程。

二、场景模拟：电商购物助手

以电商购物助手为例，用户下达指令"购买三件白色 L 码卫衣"，典型故障场景如下。

1. 假成功（Phantom Success）

Agent 调用下单工具，后端因库存不足回滚事务并返回失败。Agent 将含糊的输出误判为成功，向用户反馈"订单已创建"，实际并无订单。

2. 重复写入（Duplicate Write）

Agent 调用支付工具超时，后端实际已处理成功，仅响应丢失。Agent 重试后再次执行成功，用户被重复扣款。此外，工作流执行中途崩溃后从起点重跑，同样会生成重复订单。

3. 过期数据（Stale Data）

Agent 将历史查询结果（如库存 100 件）保留在上下文中。库存后续被其他渠道清零，Agent 未重新查询，基于过期数据下单导致失败；若基于过期价格向用户承诺，价格差异将引发纠纷。

4. 崩溃丢失状态（State Loss on Crash）

下单流程包含五步：查询库存、锁定库存、创建订单、支付、通知。流程执行至第三步时服务崩溃，重启后状态丢失：既无法确定执行进度，也无法释放已锁定库存，导致库存资源悬挂；或从头重跑导致重复扣款。

基于上述故障场景，需回答九个设计问题：

1) 权威数据源如何确定？
2) 数据归属如何划分（Agent 与后端各持有何种数据）？
3) Agent 可查询数据库，是否允许直接修改？
4) 何种数据需要强一致，何种数据允许最终一致？
5) 版本冲突、重复请求、并发修改如何处理？
6) Agent 中断、超时或重复运行后如何恢复执行？
7) 输入、决策、工具调用与数据变更如何留痕？
8) 如何限制 Agent 的读写范围与高风险操作？
9) 后端数据变更如何通知 Agent？

三、解题思路

1. 数据分层

将全部数据划分为三层，作为设计基础：

- 业务事实层：用户、订单、库存、账户，仅存于后端，为唯一权威源；
- 执行状态层：对话、计划、checkpoint、中间推理，仅存于 Agent 运行时；
- 上下文缓存层：Agent 工作记忆中的业务数据副本，性质为缓存，允许失效，但必须可刷新。

分层判定标准：数据是否为多系统共享的事实。共享事实归属后端；仅服务于 Agent 推理过程的数据归属 Agent。

2. 九个问题的设计原则

1) 权威源唯一：后端为业务数据的唯一权威源。Agent 上下文中的业务数据与后端冲突时，一律以后端为准。

2) 归属划分：按上述三层划分。业务事实归属后端，执行状态归属 Agent，副本明确标记为缓存。

3) 写路径收敛：Agent 仅通过 API/MCP 工具读写业务数据，禁止直连数据库。直连修改将把事务、校验与审计职责转移至不可信组件。

4) 一致性分级：涉及资金、库存、账户余额的数据要求强一致，由后端事务保证；Agent 上下文副本与分析结论允许最终一致，通过事件刷新。判定标准：影响用户资产与事实记录的数据要求强一致；仅影响 Agent 认知范围的数据允许最终一致。

5) 幂等与并发控制：重复请求通过幂等键（Idempotency-Key）控制，同一幂等键的多次请求仅生效一次；并发修改通过版本号与乐观锁（If-Match: version）控制，冲突时返回 409 与最新数据，Agent 重新读取并重新决策。幂等解决同一操作重复执行问题，乐观锁解决并发修改问题，二者不可混用。

6) 状态与事务分离：checkpoint 仅记录流程执行进度，业务事务一律在后端 API 内原子完成。恢复协议：重启、恢复 checkpoint、从后端重读业务状态、确定下一步动作。超时后结果未知时，先查询后端当前状态再决策，禁止基于猜测执行。

7) 全链路审计：Agent 侧记录每步的输入、推理摘要、工具调用与结果；后端侧所有写操作留痕（操作者、时间、变更内容、依据）。两侧日志以统一 trace_id 关联，支持因果链还原。

8) 最小权限与人工把关：Agent 仅可调用工具白名单内的操作；支付、退款、删除等高风险操作须人工确认或二次复核；后端鉴权体系将 Agent 作为独立低信任调用方管理。

9) 事件驱动：后端数据变更通过事件（webhook、SSE、消息队列）推送至 Agent，Agent 订阅后刷新上下文；关键操作前主动重查作为兜底。轮询为最后手段。

四、最终方案：具体设计

1. 总体架构

Agent 运行时（LangGraph 等）
    持有：对话、任务计划、checkpoint、中间推理
    不持有：任何业务数据
    |
    | 业务操作仅通过 API / MCP 工具
    v
后端服务（事实源 + 能力网关 + 安全边界）
    命令式 API：下单、支付、退款等
    幂等表、版本号乐观锁、outbox 事件
    鉴权、校验、审计
    |                          |
    v                          v
业务数据库                消息队列 / SSE
（业务数据唯一权威源）     推送变更事件至 Agent，
                          刷新上下文缓存

checkpointer 部署于 Agent 运行时侧，仅存流程状态，与业务库物理隔离。

架构核心约束：Agent 负责决策，后端负责事实，业务操作仅通过 API 一条路径。

2. 正常路径：下单流程时序

用户下达指令后，标准执行流程：

1) Agent 调用查询库存工具，获取最新库存与当前版本号（v7）；
2) Agent 决策：库存充足，执行下单；
3) Agent 调用创建订单 API，携带 Idempotency-Key（任务唯一标识）与 If-Match: v7；
4) 后端在单事务内完成：版本校验、库存扣减、订单创建、审计记录、outbox 事件写入；
5) outbox 将库存变更事件推送至队列，Agent 订阅后刷新上下文中的库存副本；
6) Agent 在 checkpoint 中记录"订单已创建，下一步：支付"。

关键分工：业务事实由后端事务产生，checkpoint 仅记录进度，不复制业务数据。

3. 异常路径：三类故障的处理

超时重试：
支付请求超时后，Agent 以相同幂等键重试。后端幂等表命中已成功处理的记录，直接返回首次结果，避免重复扣款。若幂等表未命中，说明首次请求未达后端，本次重试即为首次执行，同样安全。

版本冲突：
请求携带 If-Match: v7，库存已被其他操作更新至 v8。后端返回 409 与最新库存。Agent 基于新数据重新决策：向用户确认或调整方案。设计要求：冲突触发重读与重新决策，而非覆盖写入。

崩溃恢复：
流程执行至第三步（订单已建、未支付）时 Agent 崩溃。恢复流程：
1) 从 checkpointer 恢复 checkpoint，定位卡点（支付步骤）；
2) 不信任 checkpoint 中的业务结论，查询后端订单真实状态；
3) 基于真实状态决定继续支付或向用户确认。
同时，每日执行 reconciliation 对账任务，比对 Agent 日志与后端数据（如"Agent 记录已通知，通知表无记录"），发现不一致即告警并修复。对账为最终一致性的兜底机制。

4. 设计原则的落地手段对照

- 权威源唯一 → Agent 侧不建业务表，业务库仅归后端；
- 写路径收敛 → 业务操作全部封装为工具，Agent 不持有数据库凭据；
- 幂等控制 → 后端建立幂等表（幂等键唯一约束），先查后写；
- 乐观锁 → 关键业务表增加 version 字段，更新语句携带 where version = ?；
- 强一致 → 资金与库存变更置于同一数据库事务；
- 状态分离 → checkpointer 独立部署，与业务库物理隔离；
- 审计 → 写操作统一经过审计中间件；Agent 日志携带 trace_id，与后端日志关联；
- 最小权限 → 工具白名单；高风险操作要求人工确认；
- 事件驱动 → outbox 模式，保证事务提交与事件发送的一致性。

5. 后端角色定位与演进趋势

后端职责收敛为三项：事实源（System of Record）、能力网关、安全边界。

演进趋势：
- "记忆即服务"：会话、记忆、checkpoint 将沉淀为独立中间件，成为 Agent 架构的标准组件；
- 可观测性升级：监控重心由接口可用性转向决策链可回溯性，审计与回放能力将成为系统标配。

结论：Agent 负责决策，后端负责事实，二者通过幂等、版本、事件、审计机制衔接。允许 Agent 持有业务数据即引入第二数据源，必然产生一致性风险。
